Play a movie on the board.
Then make it longer than the board can hold.

The first version uses raw RGB565 frames: 184 × 224 pixels, ten frames per second, no audio.
The computer does the conversion.
The board reads one frame at a time.

```c
// Read outside the display lock: the UI can keep drawing the previous frame.
bool ok = sd_file ? fread(staging, 1, FRAME_BYTES, sd_file) == FRAME_BYTES
                  : esp_partition_read(media, index * FRAME_BYTES, staging, FRAME_BYTES) == ESP_OK;
if (!ok) {
    ESP_LOGE("media", "Movie read failed at frame %u", (unsigned)index);
    break;
}
// LVGL must never draw a frame while we are overwriting its pixels.
bsp_display_lock(0);
lv_image_cache_drop(&frame);
memcpy(visible, staging, FRAME_BYTES);
lv_obj_invalidate(image);
bsp_display_unlock();
```

This excerpt comes from the playback loop.
The full implementation creates an RGB565 image descriptor, allocates two frame buffers in PSRAM, loops at the end of the clip, and reports its submission rate over serial.

One buffer receives the next frame.
The other holds the pixels LVGL is allowed to draw.

## Convert a movie

Run this on your computer, with [FFmpeg](https://ffmpeg.org/ffmpeg.html) installed:

```sh
ffmpeg -i input.mp4 -t 3 -an \
  -vf "fps=10,scale=184:224:force_original_aspect_ratio=decrease,pad=184:224:(ow-iw)/2:(oh-ih)/2:black,setsar=1" \
  -c:v rawvideo -pix_fmt rgb565le -f rawvideo movie.rgb
```

This makes a silent clip up to three seconds long, fitted inside a 184 × 224 frame with black padding.
The firmware displays it at its native size in the center of the panel.

The raw format contains no width, height, or frame-rate metadata.
The conversion settings and firmware constants must agree. [FFmpeg rawvideo documentation](https://ffmpeg.org/ffmpeg-formats.html#rawvideo)

The included sample is generated by `python3 scripts/make-media.py` from the repository root.
It contains thirty frames, or three seconds at the target rate.

## How much fits?

The board has 16 MB of flash and 8 MB of PSRAM.
Flash stores the program and assets between boots.
PSRAM holds working data while the board is running. [Waveshare board documentation](https://docs.waveshare.com/ESP32-S3-Touch-AMOLED-1.8)

For storage calculations, use the actual flash capacity: 16,777,216 bytes, or 16 MiB.

```text
One frame:       184 × 224 × 2 = 82,432 bytes
One second:      82,432 × 10  = 824,320 bytes
Three seconds:   824,320 × 3  = 2,472,960 bytes
Two RAM buffers: 82,432 × 2   = 164,864 bytes
```

The entire movie does not need to fit in RAM.
Its frames arrive one at a time.

The previous lessons' original default partition table gave the app only 1 MiB.
This day's custom table reserves 3 MiB for the application and 12 MiB for raw media:

```csv
# Name, Type, SubType, Offset, Size, Flags
nvs,data,nvs,0x9000,0x6000,
phy_init,data,phy,0xf000,0x1000,
factory,app,factory,0x10000,0x300000,
media,0x40,0,0x310000,0xC00000,
```

The media partition is an application-defined raw partition, with no filesystem overhead.
This layout leaves 960 KiB after the media region and provides no OTA app slot.
It is a deliberate budget for this lesson, not a hardware limit. [ESP-IDF partition tables](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32s3/api-guides/partition-tables.html)

With this 3 MiB app allocation, all the flash from `0x310000` to the end of the chip totals 13,565,952 bytes.
Using that entire remainder would fit 164 of our frames, or 16.4 seconds at ten fps.
Doing that requires increasing both the media partition size and the build's capacity check; the shipped example uses the round 12 MiB budget below.

| Raw RGB565 frame | Pixel bytes per frame | Target fps | Complete frames in 12 MiB | Clip duration at target rate |
| --- | ---: | ---: | ---: | ---: |
| 184 × 224 | 82,432 | 10 | 152 | 15.2 seconds |
| 368 × 448 | 329,728 | 10 | 38 | 3.8 seconds |
| 368 × 448 | 329,728 | 20 | 38 | 1.9 seconds |

These are capacity calculations.
They do not establish that the board can draw any of those frame rates.
Doubling both dimensions uses four times the pixel storage.

To change the built-in clip, replace `firmware/main/movie.rgb`, then rebuild.
The build checks the media partition's capacity and passes the clip's byte length to the application.
It also includes the movie partition in the flash targets and merged image.
The app stops at the clip's real length, not at the end of the partition's unused space.

## Play from the SD card

Yes—the Waveshare board has an onboard microSD/TF slot, and its BSP already provides `bsp_sdcard_mount()`.
The installed implementation uses SDMMC in 1-bit mode, with CMD on GPIO 1, CLK on GPIO 2, and D0 on GPIO 3.
There is no external reader to wire to the board.

Convert a longer movie with the same command, removing `-t 3`.
Copy `movie.rgb` to the root of a FAT32-formatted microSD card, safely eject it from your computer, insert it in the board, and reset.
Use an existing suitable card; formatting a card erases its contents.

The firmware mounts the card at `/sdcard` and opens `/sdcard/movie.rgb`.
It checks that the file is nonempty and contains a whole number of frames.
If the card or valid file is missing, it plays the built-in flash clip instead.
Automatic formatting on mount failure is disabled.

Watch the serial log for `source=SD` or `source=flash` so a successful fallback isn't mistaken for an SD test.
Leave the card inserted during playback.

One minute of this raw format needs 49,459,200 bytes, about 47.2 MiB.
An hour needs about 2.76 GiB.
The card moves the storage limit, while the frame buffers stay the same size.

No maximum card capacity has been verified for this setup.
Card compatibility, filesystem support, and sustained read performance need testing separately from the manufacturer's slot specification.
This first implementation also uses `fseek`/`ftell`; keep individual clips below 2 GiB until large-file support is explicitly implemented and tested.

## What about MP4 or MJPEG?

This player expects raw RGB565 frames.
Copying an MP4 to the card doesn't turn it into a supported file; renaming it doesn't convert it either.

A useful next step is MJPEG: compressed JPEG frames played in sequence.
That needs a frame parser and JPEG decoder in the firmware.
Here is a conversion target for that future player:

```sh
ffmpeg -i input.mp4 -an \
  -vf "fps=10,scale=184:224:force_original_aspect_ratio=decrease,pad=184:224:(ow-iw)/2:(oh-ih)/2:black,setsar=1" \
  -c:v mjpeg -q:v 5 -pix_fmt yuvj420p -f mjpeg movie.mjpg
```

JPEG frame sizes vary with the picture and quality setting.
Measure the converted file rather than estimating from resolution alone.
For example, **if** its frames averaged 12 KiB at ten frames per second, 12 MiB would hold about 102 seconds of compressed frame data.
That is an example budget, not a measurement or a promise about decoder speed.

Audio would add its own storage, output setup, and synchronization work.
Today's assignment ends with silent video.

## Build and check

Build with `idf.py build merge-bin`.
Check that `build/flasher_args.json` lists the media image at `0x310000`, then verify that the same bytes appear there in the merged binary.

Test flash playback first, then a card containing a longer converted clip.
Check the actual picture, loop boundary, `source` log, submission rate, late-frame count, and memory use during an extended run.
Serial submission rate counts frames handed to LVGL; it does not prove how many complete frames reached the panel.

Test a missing card, a missing file, and a file with an incomplete final frame.
The first two should select the flash demo; invalid file lengths should be rejected.
Record which card and filesystem were tested before publishing SD playback claims.

Add the verified download and one-command flash instructions after hardware testing.

## The idea

Storage decides how much movie we can keep.
Memory decides how much we can hold at once.
Reading and drawing decide how quickly it moves.

The movie can be larger than memory because it never arrives all at once.
